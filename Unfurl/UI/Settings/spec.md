# Subsystem Spec: Settings Window

## Metadata

- **Title**: The Settings window with toolbar-style tab pages.
- **Surface**: a standard titled window, shown from the menu's "Settings..." item.
- **Actor isolation**: main-actor.
- **Related code**: `Unfurl/SRSettings.swift` (every control binds a preference); `Unfurl/UI/Menu/spec.md` (owner and entry point); `Unfurl/Posture/spec.md` (the nudge settings this window edits); `Unfurl/UI/Statistics/spec.md` (the statistics window that briefly lived here as a tab); `VISION.md` next to this file (the long-term plan).

## Summary

- **What this subsystem is**: the app's one configuration window: a normal `NSWindow` whose content is an `NSTabViewController` in toolbar style (the System Settings look), with a General page, a Posture page, and a Notifications page.
- **One-sentence contract**: every control reflects its bound preference live and writes it back on change; the window has no side effects beyond preferences and the calibration funnel.

## Scope

- **In scope**: `SRSettingsWindowController` (window + tabs), `SRSettingsGeneralViewController`, `SRSettingsPostureViewController`, `SRSettingsNotificationsViewController`, and the two-way binding controls in `SRSettingsControls.swift` (`SRPreferenceSwitch`, `SRPreferenceCheckbox`).
- **Constraints / assumptions**:
  - Shown via the About-window recipe (`makeKeyAndOrderFront` plus `NSApp.activate`) plus `orderFrontRegardless`, never by changing the activation policy - that stays owned by the Dock tile controller. The regardless-ordering matters: with the Dock tile off the policy is `.prohibited`, activation is refused, and without it the window opens behind the active app. It is a one-time jump to the front, not a floating level; other windows cover it normally afterwards.
  - Placement (the app-wide rule for summoned windows, defined here and referenced by Statistics, About, Welcome, and Posture): the first open centers on the interaction screen - the one holding the pointer at the menu click (`NSScreen.interaction` in `UI/SRWindowPlacement.swift`) - never `NSScreen.main`, which for a menu-bar agent with no key window falls back to the primary display and opened the window on the wrong screen when docked. Placement is decided once, at presentation: the kept instance means a reopen shows the window where the user left it, and an open window is never moved by the app. The calibration window is the one deliberate exception - it follows its camera's display (Posture/spec.md).
  - No page attaches to the camera session yet; the window consumes nothing from `SRCameraService`.

## Responsibilities and ownership

- **Responsibilities**:
  - General page: Track Posture switch, Show Camera Panel switch (`cameraPanelPinned`), Show Camera in Menu Bar switch (`showCameraOnStatusBar`), Prefer External Display Camera switch (`preferExternalCamera`, default on: while Automatic, a monitor's camera takes over the built-in when docked - see `Unfurl/Tools/spec.md`), Open at Login switch (`launchAtLogin`).
  - Posture page: one shared label axis for the whole page (the classic pref-pane form), split into two groups by a full-width separator rule, each group opened by a leading semibold header ("Cameras", "Tracking Strictness" - headers take Title Case). Row labels right-align to a single colon column; controls sit in the control column after it. The camera rows are the exception (2026-08-13): they span the page under their header with a small leading indent, the System Settings idiom - left in the control column they had the label column sitting empty beside them, and a hole reads as a mistake. The cameras group up top: one row per connected camera, two lines each - the camera's name with a Calibrate/Recalibrate button pinned to the trailing edge (all camera buttons share one width: stacked, they read as a column), and under it in small secondary text its calibration state ("Calibrated <date>" from that camera's `PostureBaselines` entry, the date relative - today/yesterday - while it applies, or "Not calibrated", prefixed "In use" plus a middle-dot separator on whichever camera is running). Two lines rather than one because a name, a full date and a button on one line stretched the window past the width the other tabs use, and the tab view sizes the window to the selected page. "In use" is text on the second line rather than a leading checkmark, which was tried first: a checkmark gutter indents every camera name past the axis the strictness rows start on, and the page is built on having one such axis; the text also reads under VoiceOver, where a bare glyph does not. Every trailing edge shares one axis: the camera rows end where the strictness rows do (their width is the page minus the indent), and the strictness sliders absorb whatever their end labels leave rather than sitting at a fixed width that stopped short of it. (A `Cameras:` colon label opened the group until 2026-08-13; the header replaced it, see below.) Replaced a single baseline line for the active camera on 2026-08-11: one "Baseline:" row taught the opposite of the truth, that a calibration covers every camera, which is what makes a new-camera nudge read as a nag rather than a next step; the laptop calibrated and the monitor not, side by side, is the whole explanation. Connected cameras only - a stored baseline keeps an id and a date, never a device name, so an absent camera cannot be labelled with anything a user would recognise. Rows are rebuilt wholesale on any change to the devices, the baselines, the active camera or the tracking toggle (four cells on a normal desk; diffing would cost more than it saves), the buttons enabled only while tracking is on, each carrying its camera's id so the funnel knows which was asked for. The verb splits on whether a baseline exists, because whether this camera has ever been set up is the point of the list. A third "Partially calibrated <date>" state existed from 2026-08-03 to 2026-08-10, for an entry with no usable slouch span; calibrated is binary again now that the span is gone, see `Unfurl/Posture/spec.md`. Then the rule, then the strictness group under its "Tracking Strictness" header. Calibration reads first because it defines the baseline the strictness is measured against; the rule keeps the baseline and its button together rather than stranding the button below the sliders. Both groups carry a header (2026-08-13, was strictness-only): the old rule - a header only where the rows do not explain themselves - was information-tidy but read as imbalance, one group opening bold and left, the other with a colon label on another axis. One idiom for the page won. The rule carries a group-sized gap above and below (about twice the 10pt row spacing) so the two groups read as separate; the rows themselves keep the 10pt rhythm the General and Notifications tabs use, so page density stays aligned across tabs. The cameras row pulls 4pt tighter to its header: its first row is button-tall and the name centers inside it, so without the trim the two groups hang different distances under their headers.
  - The strictness sliders (`SRPreferenceStepSlider`, a two-way binding control like the switch and checkbox) are tick-marked five-stop ladders, relaxed on the left: `PostureSlouchStrictnessIndex` (which stop of the ladder, 0...4, default 2 - the stop's meaning in percent below baseline is set per camera regime, see `Unfurl/Posture/spec.md`) and `PostureShoulderTolerance` (18/15/12/9/6 percent tilt slope, default 15, the tolerance value itself). Each row is named for its metric alone (Slouch, Shoulder tilt) so the label fits the pane; the "Tracking Strictness" header above carries the strictness framing, and the ends are labeled (Relaxed / Strict), the System Settings tick-slider convention. An off-ladder stored value selects the nearest stop. "Tracking", not "Notification", because these thresholds define what counts as bad posture - for the nudges and the recorded statistics alike (see `Unfurl/Posture/spec.md`) - not just when a nudge fires. They live here rather than on Notifications for the same reason. Always enabled: configuration of intent, like everything on this window.
  - Notifications page: the nudge delay popup (5 s / 10 s / 20 s / 30 s / 1 m / 5 m writing `PostureNudgeDelaySeconds`; an off-list stored value selects the closest step), the three channel checkboxes (corner note, sound, status-item tint) stacked under a single "Notify with" label with each channel's own sub-option nested one indent beneath it, so the dependency reads spatially rather than by a repeated label: the note's ghost-mode checkbox ("Fade under the pointer", `PostureNoteGhost`; enabled only while the note channel is on) sits under the note, the sound picker (bare, no repeated "Sound" label; enabled only while the sound channel is on; selecting persists the name and plays it once as a preview) sits under the sound, and the status-item tint has no sub-option. The "Notify with" label baseline-aligns to the first checkbox. and, set apart above by a full-width separator rule (the same group-sized gap the Posture tab uses, because Snooze is a temporary pause rather than delivery configuration), the snooze popup, rebuilt on every deadline change to mirror the menu's states: idle it shows "Off" over the durations; while snoozed it shows an inert "Until <time>" state line, the durations, and an explicit Resume Now item, so turning a snooze off is always one visible choice away. The popup is enabled only while Track Posture is on, because with tracking off the composition root clears any snooze write immediately (the master toggle means a clean slate).
  - The window title follows the selected tab, like System Settings; each page sets its own preferredContentSize, so the window resizes per tab, also like System Settings. All pages share one width (540) for horizontal stability; height is each page's fitting height with no floor, so a page hugs its content instead of padding out to a fixed minimum (the per-tab resize is the toolbar-preference convention, and content-fit keeps a sparse tab from showing dead space below its rows).
  - Home-window experiment, tried and reversed (2026-07-28, same day): the window was briefly the app-named home window - Statistics tab first, one fixed page size, opened at launch on Statistics, title no longer following the tab. Reversed to keep the app a quiet menu-bar agent: no main window, nothing opens at launch except the first-run welcome. Statistics moved to its own window (`Unfurl/UI/Statistics/spec.md`); this window went back to being purely Settings.
- **Owned invariants**:
  - Controls bind to raw preferences; camera availability is deliberately not consulted here. This page configures intent; the surfaces themselves explain an unavailable camera. (The menu makes the opposite choice and gates on availability; both are recorded decisions.)
  - A preference change made anywhere else (menu, hotkey) updates the visible control live, and vice versa - the menu and this window can be open at once and never disagree.
  - `SRMenuController` owns the single instance (the About precedent) and keeps it across closes, so the window and its selected tab survive reopening.
  - A row's Calibrate button behaves exactly like the menu's Calibrate item: clear any snooze, then the one shared calibration funnel, so a second calibration window can never appear. It passes its camera's id through that funnel, so a row for a camera that is not active calibrates that camera (the funnel's temporary device override) instead of whichever one happens to be running.

## Requirements

- **Native fidelity**: real `NSTabViewController` toolbar tabs, SF Symbol tab icons, `NSSwitch`/checkbox/popup system controls; window `toolbarStyle` is `.preference`.
- **Concurrency**: main-actor throughout; bindings ride the preference publishers.
